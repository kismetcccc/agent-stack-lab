# 组件地图：不是越多越好

> 当前范围：API、MySQL、Kafka、MongoDB、Redis。下表包含未来全景；可选学习前端和同源网关正在独立验收；其他新增外围组件仍暂停，不能据此认为已安装或验收。

## 主链路

| 组件 | 本项目作用 | 不用它会怎样 | 当前边界 |
|---|---|---|---|
| React/TypeScript | 登录、任务、结果与教学页面 | 可先用 HTTP 客户端，但不容易观察用户流程 | 页面不能自己假定任务成功 |
| Nginx | 静态文件、同源反向代理 | 开发服务器可临时代替；跨域配置需另处理 | 不是完整 API 管理平台 |
| FastAPI | 输入/响应契约、身份校验、业务入口 | 任何成熟框架都能承担，Python契合AI学习 | 框架不自动提供业务幂等 |
| MySQL | 关系与事务账本、outbox/inbox、租约 | 小项目可用另一关系库，但应保留事务约束 | 单实例开发，不含高可用 |
| Kafka | 持久事件日志、消费组、重放 | SQL队列也能完成小规模后台任务；这里为学习事件交付保留 | 单节点，无跨系统 exactly-once |
| MongoDB | 不同执行结果的文档结构 | 初版可存 MySQL JSON；独立引入是教学选择和后续文档查询空间 | 单文档幂等写；无跨库事务 |
| Redis | TTL进度提示 | 仍能从MySQL查询任务；不影响正确性 | 已实现不可变结果cache-aside与cache_status；完整缓存失效/限流课程待扩展 |
| Worker | 后台交付、执行、恢复 | API中做长调用影响请求生命周期与恢复 | 首轮单实例，多个内部模块 |

四种基础设施全用并不是所有真实项目的最小解。本项目有明确教学目标，才有意保留其区别。新项目应先问业务需不需要。

## Kafka 与传统工作队列

Kafka 保留分区日志，消费者以 offset 记录位置，适合事件流、多个消费组和重放。传统任务队列（如 RabbitMQ 的工作队列用法）强调消息交给处理者、确认、重新投递及路由；它也有更多模式，不能简单说只会“取走删除”。

本项目选择 Kafka 是为了学习日志、分区与事件交付；不再同时引入 RabbitMQ/Celery 形成两套任务调度。延迟重试由 MySQL 的 next_attempt_at 与 recovery 负责，而不是假装 Kafka 自动拥有任意延迟任务。小型产品完全可以先用数据库任务表，再按需求引入消息系统。

## MySQL 与 MongoDB

MySQL 的关系模型、唯一约束与多行事务使“任务＋outbox一起成功”自然；MongoDB 的文档适合不同结果结构，但仍需要索引、schema版本和访问设计。MongoDB也支持事务，不能说“文档数据库没有事务”；这里不使用它来制造跨MySQL原子性。[官方原子性说明](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)

Redis 即使开启 AOF，也不自动变成项目的权威账本。权威来自明确的业务设计、恢复协议和约束，不来自“配置了持久化”。当前进度可以丢失，最终状态不能丢。

## Kubernetes 对照表

| 对象 | 解决的问题 | 不解决的问题 |
|---|---|---|
| Deployment | 声明Pod副本、更新和重建 | 任务幂等、数据库高可用 |
| Service | 稳定服务发现与流量入口 | 用户认证、业务授权 |
| ConfigMap | 非秘密配置 | 密钥保密 |
| Secret | 分离敏感配置与源码 | 默认就完成静态加密、日志脱敏 |
| PVC | Pod重建后继续挂载数据 | 备份、跨节点高可用、删除集群后的恢复 |
| liveness probe | 判断进程是否应重启 | 外部数据库坏了就该重启所有API |
| readiness probe | 判断是否适合接收流量 | 一次任务是否业务成功 |
| Job | 运行迁移等一次性任务 | 自动保证迁移回滚 |
| NetworkPolicy | 支持它的CNI下限制网络路径 | 默认Kind一定执行策略 |

Kubernetes清单与运行实验当前延期；此表仅用于以后阅读，不表示当前已经部署。数据库用开发用单副本部署也不代表真实数据库集群设计。

## 更完整的传统后端分类（原理比较/后续计划，非本轮已实现）

| 类别 | 常见选择 | 学习问题 | 优先顺序 |
|---|---|---|---|
| 网关/反向代理 | Nginx、APISIX | TLS终止、路由、限流、入口治理；与应用授权的边界 | 核心API后 |
| 对象存储 | S3兼容存储 | 为什么文件不直接塞进业务表？授权URL如何过期？ | 有附件需求时 |
| 搜索 | OpenSearch、Elasticsearch | 倒排索引、搜索相关性、写入到可搜索的延迟 | SQL查询清楚后 |
| 集中身份 | Keycloak | OIDC/SSO、身份提供方、应用资源授权 | 本地会话理解后 |
| 调度 | APScheduler、Quartz、XXL-JOB | 定时触发、持久化、错过执行与重复触发 | 可靠异步之后 |
| 长工作流 | Temporal | 长任务状态、恢复、补偿、人工等待；不等于普通消息队列 | 复杂多步需求出现时 |
| 日志 | Loki、ELK | 收集、检索、保留、脱敏；不是指标库 | 排障需求出现时 |
| 指标/面板 | Prometheus、Grafana | 计数器/直方图、告警、标签基数 | 主链路稳定后 |
| 分布式trace | OpenTelemetry、Jaeger | 埋点、上下文传播、采集与查看的分工 | 能解释每段调用后 |
| 配置/服务发现 | Nacos、Consul | 服务地址和配置如何更新，与Kubernetes原生能力的重叠 | 确有多服务需求时 |
| 构建交付 | Docker、CI、镜像仓库 | 可复现构建、测试、镜像版本、回滚 | 核心开发同步学习 |

**同类是备选，不是全部安装清单。** OpenTelemetry偏采集/标准，Jaeger偏trace存储与查询；Grafana面板不替代Prometheus指标采集。Quartz偏Java调度生态，APScheduler适合Python进程集成，选择还取决于持久化与多实例语义。产品版本、许可证、运维成本应在真正选型时再核实。

以下常见后端能力通常是代码/库/流程，不必另起服务：ORM、schema迁移、连接池、输入校验、超时预算、熔断、重试、幂等、事务、备份恢复。先学习它们的正确语义，再考虑独立平台。
